# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BolicBuddy ("Bolic") — a fitness social-networking mobile app: partner/trainer matching, workout tracking, groups, real-time chat, trainer booking with Stripe payments. Expo + React Native, TypeScript (strict), React 19, New Architecture enabled.

**Open questions for the client are tracked outside this repo** (a shared
questions doc) — there is no `CLIENT-ASK.md` here any more, so don't cite one.
Asks for the API team live in **`BACKEND-ASK.md`**, which lists *only* what is
still open: answered items were deleted rather than annotated, item numbers are
the originals and deliberately non-contiguous (a missing number means closed),
and new items continue from 61. Read it before assuming a response shape or
inventing a value to display.

Release blockers still outstanding: the **Privacy Policy and Terms URLs**
(nothing can be submitted to either store without them) and the **ArcGIS
geocoding licence** — though the move to device GPS may retire that one, since
it is *storing* geocoded coordinates that requires the paid tier. Answered by
the business: units are **US standard (miles, pounds)**, and the refund policy
follows **Stripe's standard** — full refund, no cancellation fee, 5–10 business
days (the values to set server-side are `BACKEND-ASK.md` item 67).

A disposable API test account exists (credentials live with the team, not in
this repo), so response shapes can be measured rather than guessed.

Large parts of the product are still placeholder — screens can look complete while their controls do nothing and their numbers are hardcoded. Verify a screen actually works before building on it. **The booking / trainer-availability flows in particular shipped fabricated data** — invented time slots, an invented refund fee and timeline, and a pre-filled Mon–Sun 9–5 trainer week. Those are gone; see **No invented data** below.

**Verification status.** Run against the live API on a booted simulator, on
**both** a trainer and a non-trainer account: Home, Find (filter chips,
compatibility badge, the rating sheet), Groups + create-group, Profile on both
branches, `TrainerAvailability` (including Discard), `Settings`, `Achievements`,
`WorkoutHistory` (including "Post it" end-to-end — the post really does carry
its `sessionId` and logged sets), and `SelectWorkout`.

**Gotcha:** `Achievements`/`WorkoutHistory`/`Schedule Sessions` render only on
the **non-trainer** branch of `ProfileScreen` — a trainer account sees All
Bookings / My Availability / My Pricing / My Ratings instead — so you need a
non-trainer login to reach them at all.

Still unverified at runtime: checkout past the date picker (needs a Stripe test
card), chat, and anything needing a second account with coordinates. And
`navigation: any` means `navigate()` calls are never type-checked (see
Navigation below).

## Commands

```bash
npm start            # expo start (Metro bundler; press i/a for simulators)
npm run android      # expo run:android (native dev build)
npm run ios          # expo run:ios
npm run type-check   # npx tsc --noEmit — the reliable way to validate changes
npm run prebuild     # regenerate native android/ios dirs (they are gitignored)
```

- **Validation:** use `npm run type-check`. `npm run lint` is defined in package.json but **ESLint is not installed and there is no config**, so it will not run as-is. There are **no tests** (`npm test` is a placeholder).
- **`.npmrc` sets `legacy-peer-deps=true`** — required for `npm install` to resolve.
- **`npm install` re-applies patches** via `patch-package` on `postinstall`. `patches/@stripe+stripe-react-native+0.50.3.patch` flips `STPPaymentStatus` from `NS_ENUM(NSUInteger, …)` to `NSInteger` in that SDK's `ios/StripeSwiftInterop.h`; without it the iOS build fails with *"enumeration redeclared with different underlying type"*, because clang in Xcode 26 rejects a signedness mismatch older clang tolerated. **Gotcha:** always regenerate scoped — `npx patch-package @stripe/stripe-react-native --include 'ios/StripeSwiftInterop\.h'` — since unscoped it sweeps several hundred Android build artifacts into the patch.
- **Gotcha:** `pod install` (so also `npm run ios`) fails unless the shell locale is UTF-8; set `export LANG=en_US.UTF-8`. Ruby 4.x defaults to ASCII-8BIT and CocoaPods calls `unicode_normalize` on the project path. Expo reports this only as a generic "pod install failed", and the build then dies on a misleading *"sandbox is not in sync with the Podfile.lock"*.
- **Native builds** go through EAS (`eas.json` defines `development`/`preview`/`production` profiles; helper scripts in `scripts/build.sh` / `build.bat`). `android/` and `ios/` are gitignored and generated by prebuild.

## Environment / config

- Env vars use the **`EXPO_PUBLIC_` prefix** (Firebase, Stripe key). See `.env.example`. `.env` is gitignored; EAS profiles in `eas.json` carry build-time env values.
- **Gotcha:** the API base URL is **hardcoded** in `src/config/constants.ts` (`API_CONFIG.baseUrl`), *not* read from `EXPO_PUBLIC_API_URL` (the env-based line is commented out). Change the backend host there. `SOCKET_CONFIG` and `FIREBASE_CONFIG` in the same file *do* read from env.
- **There is no server code in this repo** — the backend is a separate service behind that base URL, so no claim about server behaviour can be verified from source. `BACKEND-ASK.md` separates what was established from the client from what the API team still has to confirm.
- `src/config/constants.ts` is the central config module: `API_CONFIG`, `SOCKET_CONFIG`, `COLORS` (a large hex palette with `_HEX`-style keys), `DIMENSIONS`, `STORAGE_KEYS`, `ERROR_MESSAGES`/`SUCCESS_MESSAGES`, training-type/gender option lists, **and** a set of exported timezone/date helpers (`toUtc`, `toLocalTime`, `convertLocaDatemmddyyyylToUTC`, `formatUTCToDisplayDateTime`, `addOneHourToTime`) used by the booking/scheduling flows. `TRAINING_TYPES` is the **single source** for the training-type chips (AuthScreen onboarding, FindScreen filters, `UserProfileForm`, Settings matching preferences) — drive chips from it rather than re-inlining the list. **Gotcha:** an empty string in `LEGAL_LINKS` (Privacy Policy / Terms / support) and a `false` in `FEATURE_FLAGS` both mean "hide this, it isn't ready" — not "broken". Settings hides such rows entirely rather than rendering a dead tap or an "unavailable" label; fill in the string or flip the flag and the row appears with no other code change.
- **Theme:** the app uses a **monochrome DARK theme** driven entirely by the `COLORS` object — retheme from there, not per-screen. `primary` is **white** (`#FFFFFF`) and is the accent used for primary-button backgrounds and active states; buttons are `backgroundColor: COLORS.primary` (white) + a dark label (`COLORS.surface`/`COLORS.black`); `background` `#0A0A0A`, `surface`/`card` `#171717`, `text`/`white` white, `textSecondary` `#A1A1A1`, `border` `#2A2A2A`. **Gotcha:** the legacy hex-named tokens were remapped in place, so a name like `_5E5E5E` or `app_black` **no longer equals its literal hex** — trust the role, not the name. Using one on a dark surface renders near-invisible text; several such bugs have already been fixed (e.g. in `CancellationConfirmationModal`). `gradient1/2/3` are the (dark) top-bar gradient; don't use them as text colors. Monochrome PNG icons from `assets/index` render dark and need `tintColor: COLORS.white` on dark surfaces (or `COLORS.black` on white buttons); skip `{uri}` photos and `AppLogo`. `app.json` `userInterfaceStyle` is `dark` and the splash uses `assets/app_logo.png`.

## Architecture

### Provider hierarchy (`App.tsx`)
`BolicStripeProvider` → `GestureHandlerRootView` → Redux `Provider` → Paper `Provider` → `AuthProvider` → `AppNavigator` + `ToastWrapper`. Render is gated on `useInterFonts()` (shows `LoadingScreen` until Inter fonts load).

### State: Redux Toolkit + RTK Query
- `src/store/store.ts` combines `baseApi.reducer` + `userSlice`. `serializableCheck` is **disabled** (FormData / non-serializable payloads flow through).
- Typed hooks live in `src/store/hooks.ts` (`useAppDispatch`, `useAppSelector`, plus auth selectors like `useUser`, `useToken`, `useIsAuthenticated`).
- **All server state goes through RTK Query.** `src/services/api/baseApi.ts` creates the single `baseApi` (with the full `tagTypes` list). Every feature API file **extends it via `baseApi.injectEndpoints(...)`** — do **not** create new `createApi` instances.

### API layer (`src/services/api/`)
- **Adding an endpoint:** put the URL in `src/services/endPoints.ts` (`API_END_POINTS`, grouped by domain; many are functions taking IDs/params), then add a query/mutation in the relevant `*Api.ts` via `injectEndpoints`, wire `providesTags`/`invalidatesTags` against the `tagTypes` in `baseApi.ts`, and export the generated hook. `src/services/api/index.ts` re-exports the slices.
- **Auth token** is read from AsyncStorage (`storageService.getAuthToken()`) and injected as a `Bearer` header in `baseApi`'s `prepareHeaders`.
- **FormData endpoints** must be added to the `formDataEndpoints` allowlist in `baseApi.ts` so `Content-Type` is left unset (lets RN set the multipart boundary). Endpoints doing this: profile-with-image, createPost, updatePost, sendMessage, createConversation.
- **Location & coordinates:** address autocomplete and geocoding go through `src/utils/location.ts` (`fetchLocationSuggestions`, `geocodeLocation`, `formatDistance`, over the ArcGIS URLs in `LOCATION_CONFIG`) — never `fetch` ArcGIS inline. `PUT /user/update` takes optional `latitude`/`longitude`, which `EditProfileScreen` and `UserProfileForm` resolve from the picked or typed address. **Gotcha:** the matching endpoints' `distance` is in **kilometres** (`haversineKm` server-side) but the product displays **miles** (US market) — `formatDistance` in `src/utils/location.ts` is the single place that knows either unit and does the conversion. Don't convert anywhere else. `compatibility` is a **0–100 integer** whose inputs are training types, gender fit, `matchingPreference` overlap and age — **not distance** — and it is left absent rather than `0`, so `SwipeableCard` hides its match tag instead of claiming "0% Match". `POST /matching/nearby` is live (takes `unit: "km" | "mi"`, excludes users without coordinates, sorts nearest-first) but has no consumer yet. **Gotcha:** Settings' "Matching Preferences" chips read and write **`trainingTypes`**, *not* `matchingPreference`, even though the section is named for the latter. `PUT /user/update` whitelists `matchingPreference` to only `["Strength","Cardio","CrossFit"]` and silently drops the other 11 while answering 200, so the screen showed nothing selected and failed 11 of 14 saves; `trainingTypes` accepts the full vocabulary and is where the user's onboarding choices actually live. **`matchingPreference` now has no writer in the app** (`BACKEND-ASK.md` item 59 asks what it is for). Two related server quirks the client works around: `trainingTypes: []` is ignored, so the last style can't be removed (the UI blocks it — item 65), and the catalogue holds case-duplicate rows (`"BodyBuilding"`/`"Bodybuilding"`) so a write echoes back more entries than were sent — `parseMatchingPreference` in `SettingsScreen` canonicalises case-insensitively and de-duplicates (item 66). **Coordinates now come from device GPS.** `src/hooks/useDeviceLocation.ts` requests foreground permission **on app launch** (mounted as `DeviceLocationSync` inside `AuthProvider` in `App.tsx`), reads one Balanced-accuracy fix, and PUTs `latitude`/`longitude` once a user is signed in. Two rules it deliberately keeps: it writes **coordinates only** — the `location` *text* stays whatever the user typed, so GPS never rewrites a profile's displayed location — and a **declined permission is not an error**, it silently falls back to the coordinates geocoded from that typed address. Coordinates are rounded to 3 decimal places (~110 m) so a stored position can't identify a front door, and are re-sent only after ~200 m of movement, once per app run. Address geocoding (`src/utils/location.ts`) still backs autocomplete and the no-permission fallback. All of this is measured, not assumed: `PUT /user/update` persists, echoes **and clears** the pair, and device coordinates were observed reaching the server from the simulator. **But no distance renders anywhere yet** — every candidate comes back `distance: null` because no *other* account has coordinates until the server's one-off backfill runs (`BACKEND-ASK.md` item 58). The feature is complete and invisible.
- **Gotcha: a `403` from this API does not mean the route exists.** Auth is mounted at the **router prefix**, so any path under `/workout-session/*`, `/workout/*` or `/post/*` returns `403 Unauthorized` whether or not the route is defined; only routers without prefix-level auth (e.g. `/user/*`) return a real `404 Route not found` for a missing path. So you **cannot** prove an endpoint is absent by probing it — check `src/services/endPoints.ts` for what the app declares, and ask the API team about anything else rather than concluding it doesn't exist.
- **Notifications are not implemented.** `/notifications` and `/notifications/settings` return 404, there are no notification socket events, and `src/services/api/notificationsApi.ts` + `src/components/NotificationManager.tsx` have **no consumers anywhere** — don't wire them expecting them to work. Settings' notification toggle only persists `notificationEnabled` via `PUT /user/update` and requests the OS permission; nothing delivers. Whether any of this gets built is still an open product question; the answer decides whether both files get deleted. **Gotcha if you do revive `NotificationManager`:** its `requestPermission()` calls `getExpoPushTokenAsync()` inside the same `try`, so a token failure makes it return `false` and record permission as denied even when the user granted it — and it uses `Alert` and emoji titles, both against this project's conventions.
- **Workouts payload gotchas** (`/workout/all`, `/workout/:id`): `totalDuration` is in **seconds** (`1800` for a 30-minute workout) — format it through `formatWorkoutDurationMinutes` in `src/config/constants.ts` rather than printing the raw value, which is what used to render "1800 min" in the post and group feeds. `totalDuration` now genuinely varies per workout and `totalDurationSeconds` is emitted alongside the legacy field — prefer it. **`difficulty` is still `"Medium"` on all 29 workouts** on the deployed server despite the API team reporting it derived, so every card reads "Medium" (`BACKEND-ASK.md` item 34) — don't build anything that assumes a spread. `imageUrl` plus the nested `exercise.imageUrl`/`videoUrl` are still **`null` for every workout** (a content gap — the URL plumbing exists server-side) — so cards fall back to a local PNG. Every `/workout/all` row carries a machine `category` slug (`chest`/`legs`/…/`full_body`), which `SelectWorkoutScreen` uses first for artwork, then the `GET /workout/categories` type→slug mapping, then its local alias table (in-flight/offline fallback) — never keyword-match `type`, which is free-text display copy (`"Arms Workout (Biceps + Triceps)"`). `/workout/all` also filters by `?category=<slug>` (the slug, not the display string). `/workout-session/complete-exercise` accepts `weightUnit` (`"kg"` default, `"lbs"`); `WorkoutSessionScreen` sends **`"lbs"`** explicitly (US market) and its input is labelled accordingly — send the unit rather than relying on the server default, which is kg. `WorkoutHistory` prints the unit each set was *actually* logged in, falling back to kg only for rows written before the field existed. `POST /post/create` accepts an optional `sessionId` (must be the caller's own session) — `ShareWorkoutScreen` attaches it when sharing from Workout History, and the post read models return a nested `session` (status, duration, logged `progress[]` with `weightUnit`), verified live. **No feed or group card renders that performance yet** — the data is there whenever someone builds it. `exercise.muscleGroups`/`equipment`/`instructions` now arrive as **real arrays** (the old JSON-string encoding is fixed), and `targetMuscleGroups`/`equipmentRequired` are populated. **Gotcha:** `weightUsed` and `caloriesBurned` are DECIMAL and serialise as **strings** (`"60.00"`) — run them through a `Number()` coercion. `GET /workout-session/:sessionId` exists (owner-scoped, `{ session, progress, timing }`), so Workout History's per-card `GET /workout/:id` fallback and its "Workout plan" label are only needed for legacy sessions. Post read models return a nested `session` object (duration + logged sets) when a post carries `sessionId` — **no feed card renders it yet**. The workouts endpoint defaults to `limit=10` (clamped to 100), so pass an explicit `limit` or you silently render a fraction of the catalogue.
- **Gotcha: this API reports failures as HTTP 200 with `{ status: false, message }`.** RTK Query treats that as success, so a resolved `.unwrap()` is **not** proof the call worked — check `status === false` and throw the server's `message` yourself. Several screens showed success toasts for failed writes because of this. `message` is server-audited user-presentable copy and is surfaced **verbatim**; failures also carry a machine-readable **`code`** (`SLOT_UNAVAILABLE`, `SESSION_ALREADY_STARTED`, `GROUP_PRIVATE`, `JOIN_REQUEST_COOLDOWN`, …) — branch on `code`, never on message text. One code is special: `ALREADY_CANCELED` arrives with HTTP 200/`status: true` and means an idempotent retry — treat it as success.
- `baseApi.ts` also holds cross-cutting response fixups: it coerces a 404 on `/group/members/` into an empty-list success, and normalizes `PARSING_ERROR` into a structured upstream-unavailable error. Requests/responses are verbosely `console.log`ged.

### Bookings & cancellation (`src/services/api/bookingApi.ts`)
- **Cancel with `useCancelBookingAtomicMutation()`** (`POST /booking/cancel`): one idempotent call that flips the status, refunds where a payment exists, and returns the refund figures. A retry answers 200 with `code: "ALREADY_CANCELED"` — that is success. When the cancel lands but the refund fails, `data.refund_error` carries user-presentable copy — surface it, never report plain success. The old two-call pair (`useCancelBookingMutation` + `useRefundBookingPaymentMutation`) still works but reintroduces the canceled-but-unrefunded window; don't use it in new code. **`useDeleteBookingMutation()` remains deprecated** (it hits the refund endpoint, which used to hard-delete the booking).
- **Refund figures come from `useLazyGetRefundQuoteQuery()`** (`POST /booking/refund-quote`) — snake_case keys, **minor-unit amounts (cents; divide by 100 at render)**, and `fee`/`expected_arrival`/`policy_text` stay 0/null until the business configures them server-side. Render nothing for nulls — the business has chosen full refund / no fee / 5–10 business days, so once those values are set server-side they appear on their own (`BACKEND-ASK.md` item 67). `ScheduledSessions` maps it into `CancellationConfirmationModal`'s `RefundQuote`.
- **Gotcha:** the status enum is `"upcomming" | "completed" | "canceled"` — the first is misspelled server-side (two `m`s), the last is not (one `l`). Copy the literals, don't retype them.
- Bookings carry **`payment_status`** (`"paid" | "unpaid" | "refunded" | "refund_pending"`) and a `refund` object — use them; never infer refundability from `price.price > 0`.
- The server **rejects double-booking** (`409 SLOT_UNAVAILABLE`; DB-level uniqueness, cancelling frees the slot) and **rejects cancelling a started or completed session** (`409 SESSION_ALREADY_STARTED`). Failures carry a machine-readable `code` alongside the verbatim-rendered `message` — branch on `code`.
- **Multi-slot checkout is refused server-side** (`400 MULTI_SLOT_UNSUPPORTED`). `DateTimeSelector`'s `allowMultipleSlots` prop is dead (no caller) and marked deprecated — delete it on the next rework, never wire it up.
- **Not yet adopted:** `POST /trainer-availability-slot/bookable-slots` — server-computed picker slots with taken-slot/exception awareness and correct per-date timezone math. `DateTimeSelector` still derives slots client-side from the weekly pattern (though it now uses the server's grid values), so it cannot see booked slots or exception dates.

### Trainer availability & scheduling (`src/services/api/availabilityApi.ts`)
The server owns the scheduling model. Current truths, all measured live:
- **`POST /trainer-availability-slot/list` returns an object, not an array**: the per-trainer record (exactly one; unique-indexed) sits in `data.records`, alongside grid fields (`timezone`, `has_configured_availability`, `slot_duration_minutes`, `lead_time_minutes`, `booking_horizon_days`). `getAvailability`'s `transformResponse` normalises both shapes so consumers still read an array, with the grid riding along as `grid`. `DateTimeSelector` consumes those grid values (its old 60/30/30 constants remain only as fallbacks for legacy payloads).
- **`/create` and `/update` are the same server function: full replace.** Days absent from `slots` are removed, `slots: []` means unavailable all week, and identical re-saves don't duplicate. Keep the existing update-when-a-record-exists check anyway.
- **Time format is canonical 24-hour `HH:mm` in both directions** server-side (input tolerant — verified live: `"09:00 AM"` in, `"09:00"` back). Day names come back **lowercase** (`"monday"`); every consumer matches case-insensitively.
- **Writes send wall-clock times plus the device IANA `timezone`** (injected by the API slice — `deviceTimeZone()` in `availabilityApi.ts`); there is **no `toUtc` shifting anywhere in the availability flow any more**. Display shifts only **legacy records** (`timezone` `"UTC"` or absent), whose times the old client shifted device→UTC on save — a record self-heals to the new contract on its next save. Never reintroduce client-side UTC conversion here; the server owns date-specific UTC/DST math.
- **DST/timezone is handled server-side** (IANA timezone per availability record, per-date conversion). Empty-string times are rejected with 400; absence means unavailable; per-slot ids are derived (`d{day}-{start}-{end}`), stable, and accepted by `/delete` (unknown id = harmless no-op).
- **Vacation/blackout dates exist server-side** — `/trainer-availability-slot/exceptions` (+ `/list`, `/delete`), surfaced in bookable-slots as `source: "exception"` — but **no client UI consumes them yet** — the shape just needs confirming before the trainer-side screen is built.
- `hasConfiguredAvailability` and `trainerOnboardingComplete` are **server-derived on the profile** — trust them over the client-written `trainerOnboardingStep`.

### Groups (`src/services/api/groupsApi.ts` + `src/screens/group/`)
- **Group privacy is enforced server-side now.** `/group/members/:id` and `/group/posts/:id` answer `403 GROUP_PRIVATE` to non-members (and the post controller no longer leaks private-group posts by id, via profiles, or into the community feed). `baseApi` coerces those 403s into empty-list successes so `GroupDetails` renders its privacy notice instead of an error. `/group/:id` and `/group/all` stay readable by design — a private group must be discoverable to be requestable.
- **`privacy` is validated server-side** to exactly `Public`/`Private` (matched case-insensitively, stored TitleCase); legacy `"Invite Only"` rows were migrated to Private. `ManageGroup` still carries its legacy-value save-block — vestigial once the migration is confirmed run on the deployed DB, then it can go.
- **Every group row now carries authoritative `isMember`, `joinRequestStatus`, `canJoin`, `canRequestJoin`.** `GroupDetails` prefers the flags and keeps the member-list scan and privacy-string derivation only as fallbacks — don't add new logic that infers behaviour from the privacy string.
- **Join-request lifecycle is real:** rejected requests get a 24h cooldown (`429 JOIN_REQUEST_COOLDOWN` with `data.retryAt`), `GET /group/join-requests/mine` exposes the requester's own state (`canResendAt`), and a `group_join_request_decided` socket event fires on decisions — **none of which the client consumes yet**.
- **Gotcha: group location is plain free text** — `ManageGroup` is the one location field in the app that does *not* go through `src/utils/location.ts` autocomplete, so "SF" / "San Francisco" / "san francisco, ca" are three distinct values. It replaced a dropdown of four invented areas (Downtown/Uptown/Midtown/Suburbs) that defaulted new groups to "Downtown". Reconciling it with the shared location util is outstanding.
- The server now enforces a 24-hour cooldown on a rejected join request and exposes the requester's own status, but **no client UI surfaces either** — the requester still sees nothing. `useGetUserGroupsQuery` (`/group/my-groups`) and `STRINGS.GROUPS.myGroups` both exist with **no consumer** — there is no "My Groups" view.

### Auth (`src/contexts/AuthContext.tsx`)
- **Auth state lives in Redux (`userSlice`), but is consumed almost everywhere via `useAuth()`** (27+ files) rather than the Redux hooks directly. `AuthProvider` reads Redux state and exposes `login`/`register`/`logout`/`updateUser` plus `user`/`token`/`isAuthenticated`/`isBootstrapping`.
- On mount it bootstraps: if a stored token exists it fetches a fresh profile (`useLazyGetMyProfileQuery`) and dispatches `setUser`, else `clearUser`; `isBootstrapping` gates the app's loading screen.
- `login` persists **only the token** to AsyncStorage (profile is kept in Redux). `logout` clears Redux user state, calls `baseApi.util.resetApiState()`, and wipes user keys from AsyncStorage.
- **Gotcha: phone verification is fake, and `phoneVerified` is asserted by the client.** `sendVerificationCode` in `AuthScreen.tsx` makes **no network call at all** — it puts a local `const demoCode = "123456"` into state, and `verifyCode` compares the user's input against that constant. There is no OTP endpoint anywhere in `endPoints.ts`. The only thing that reaches the server is `phoneVerified: true` on `PUT /user/update`, which the client simply claims. So **every account flagged verified is unverified in reality** — never build a trust badge, recovery flow or de-duplication on that field. Making it real needs two server endpoints (send + verify, with expiry and attempt limits) and `phoneVerified` becoming server-set and client-unwritable; the app side is then a small change.

### Navigation (`src/navigation/AppNavigator.tsx`)
- React Navigation v7. **Auth-gated at the root:** `isAuthenticated` switches between an Auth stack (`Auth`, `ForgotPassword`) and the main app.
- Main app = a **bottom tab navigator** (Home, Find, Groups, Messages, Profile) wrapped by a stack holding all detail/modal screens. Two nested stacks exist: `HomeStackNavigator` (HomeFeed → CreatePost/ShareWorkout) and `FindStackNavigator` (FindMain → UserProfile).
- **All navigation param lists are typed in `src/types/index.ts`** (`RootStackParamList`, `MainTabParamList`, `FindStackParams`, `HomeStackParams`) — update these when adding screens/params.
- **Gotcha:** screens take `navigation: any`, so **route names and params are not type-checked** — a typo'd `navigate()` fails silently at runtime and `npm run type-check` stays green (`MyBookingsScreen` shipped a dead `navigate("RescheduleSessionScreen")` against a route registered as `"RescheduleSession"`). Grep `AppNavigator.tsx` for the exact name and check `RootStackParamList` for the params the target screen actually reads.
- **Gotcha:** `ProfileScreen`'s `isGuest` route param means "viewing someone else's profile", not "logged out" — `FindScreen`/`GroupDetails`/`ManageGroup` pass `isGuest: true` alongside a `userId`.
- Deep linking configured with the `bolic://` scheme (see also `app.json` `scheme` + `apple-app-site-association` / `.well-known`), including a `reset-password` path with a `token` param.

### Real-time chat (`src/hooks/useChat.ts` + `src/services/socketClient.ts`)
- `socketClient.ts` manages a **singleton socket.io client** (`initializeSocket(token)` / `getSocket` / `disconnectSocket`); the socket URL is derived from the API base URL by stripping the `/api` path.
- `useChat` is the large orchestrator hook: it merges RTK Query (`messagingApi`) data with live socket events (`new_message`, `message_status`, `message_read`, `message_reaction`, `typing`, `conversation_upserted`), does **optimistic sends** with temp negative IDs, tracks read receipts, and **manually patches the RTK Query cache via `messagingApi.util.updateQueryData`**. There's also a module-level `conversationMessageCache` for pagination state. When touching chat, keep the socket handlers and the cache-patching in sync.

### Payments (Stripe)
- `src/components/stripe-provider.tsx` wraps the app and reads `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY` (throws if missing). `merchantIdentifier`/`urlScheme` are set for Apple/Google Pay + return URLs.
- `src/utils/stripeUtils.ts` `useStripePayment()` runs the PaymentSheet flow. Note it calls the payment-intent endpoint with a **direct `fetch`** (manually attaching the bearer token), not through RTK Query. Booking create/update/refund go through `bookingApi.ts`.
- **Amounts render with a bare `$` and there is no currency handling anywhere.** Single-currency (USD) is an assumption, not a decision.

### Styling & UI conventions
- **Responsive scaling:** `src/designing/responsiveDesigns.ts` exports `r(value, type?)`, `responsive(styleObject)` (auto-scales numeric values by inferring width/height/font/spacing from the property name), `SCALE`, `wp`/`hp`, `isTablet`. Use the `useResponsive(styles)` hook (`src/hooks/responsiveDesignHook.ts`) to memoize. Base design reference is 375×812 (iPhone X). Most screens still use plain `StyleSheet.create`.
- **Fonts:** Inter, via `useInterFonts()`; reference weights through the **`FontWeight` enum** (default export of `src/hooks/useInterFonts.ts`), e.g. `fontFamily: FontWeight.SemiBold`.
- **Icons/images:** PNG assets are exported as named `require()`s from `assets/index` and imported as `import { Fire, Settings } from "../../assets"`.
- **No emoji in UI chrome.** Section titles, buttons, badges, and list rows use plain text plus a PNG icon from `assets/index` (`<Image>` with an explicit `width`/`height` + `tintColor`), never an emoji in a `<Text>`. Decorative emoji were stripped from HomeScreen; when adding UI, reuse an existing asset rather than reintroducing one. **Exception:** post reactions (`src/constants/reactions.ts`) are emoji by design — that's the feature, not decoration.
- **No calories anywhere in the UI.** The backend still computes and stores per-exercise and per-session calories (and the response types in `src/types/index.ts` still carry the fields), but nothing renders them and `WeeklyGoalType` is `workouts | minutes` only. This is deliberate — the server's estimate assumes 3 seconds per rep, so the numbers are not trustworthy. Don't add a calorie readout back.
- **No invented data, and no faked progress.** `Achievements` requests `?include=locked` on your own profile, so `/users/me/achievements` returns the full catalogue with per-user `progress`/`target`; in that mode a row counts as unlocked **only** on an explicit `earned`/`unlocked` flag or an `earnedAt` date — never by mere presence in the list — and the old diff against the `/achivement/all` catalogue remains as the fallback. It renders **no progress bar at all** when the API supplies no `progress`/`target` — and none on a locked row claiming `progress >= target` either, because the live server currently returns placeholder `progress: 1, target: 1` on every locked row (`BACKEND-ASK.md` item 36) and a full bar under a lock would be a lie. Locked rows are only shown on your own profile, since another user's progress can't be attributed. An empty `bio` or `location` renders nothing — never a canned paragraph or a default city (the old `STRINGS.PROFILE.bio`/`defaultLocation` were deleted for exactly that reason). **Gotcha (softened):** the profile endpoints' `partnersCount` used to be the platform-wide user total; the server now derives it from accepted connections, so it and `useGetUserConnectionsQuery`'s `pagination.total` (which `ProfileScreen` still uses) should agree. The trainer stat is `clientCount` (distinct clients across upcoming+completed) and the workouts stat is `totalWorkouts` — there is no `workoutsCount`/`clientsCount`.
- **No invented availability.** `DateTimeSelector` used to synthesize three days of fake time slots when a trainer had none, so clients could book hours the trainer never offered. It now renders loading / empty / error / has-slots as distinct states, with the primary button disabled unless real slots exist. Trainer setup likewise no longer pre-fills Monday–Sunday 9–5 — days start off, hours must be chosen explicitly, and only chosen days go into the payload.
- **No invented financial terms.** The cancellation sheet used to show a hardcoded 3% processing fee and a "5–7 business days" refund window, neither from Stripe nor from any spec. Refund figures render **only** from server-supplied values (`CancellationConfirmationModal` takes an optional `RefundQuote`); with nothing to show it displays the amount actually paid plus a neutral "confirmed by the payment provider" line. Never reintroduce a computed fee or timeline — the wording and figures are server-owned config (`BACKEND-ASK.md` item 67).
- **Don't let a control lie about what it does.** "Discard" in `TrainerAvailability` used to overwrite the trainer's whole week with 9–5 and *save* it; "Save Draft" in trainer setup claimed to store availability while only writing a progress step; its copy is now honest about that. If a control can't do what its label says, fix the behaviour or fix the label.
- **Copy/strings:** `src/config/strings.ts` exports `STRINGS`, organized by screen. **Gotcha:** screen copy that *looks* hardcoded is often here — e.g. the Home section titles are `STRINGS.HOME.weeklyGoal`/`workoutOfDay`/`quickNotes`, so editing the screen file alone won't change them. Grep `src/config/strings.ts` too. `STRINGS.SELECT_DATE_TIME` (the booking picker's loading/empty/error states) is **placeholder wording written by us**, not client-approved copy. **Pending cleanup:** `MyBookingsScreen`, `TrainerAvailability`, `TrainerSetup`, `TrainerSetupStep1` and `TrainerSetupStep2` each carry a local `COPY` constant with a `TODO(strings)` marker — written that way to avoid concurrent edits to `strings.ts`, and still to be moved into `STRINGS`. `STRINGS.SETTINGS.linkUnavailable` is now unused — Settings hides an unconfigured legal row rather than labelling it — and can go whenever `strings.ts` is next touched.
- **Toasts:** use the global `Toast` API from `src/components/ToastManager.tsx` (`Toast.success/error/warning/info(...)`), which drives the `<ToastWrapper/>` mounted in `App.tsx`. (Prefer this over the `toastify-react-native` dependency.) Prefer it over `Alert.alert` too, which older screens still use — replace it when you touch them.
- **Confirmation dialogs:** reuse `src/components/ConfirmationDialog.tsx` (it supports a `loading` state) or `ConfirmDialog.tsx`; don't hand-roll another `Modal`. `CancellationConfirmationModal.tsx` is specifically the booking-cancellation sheet, not a general-purpose dialog. **Gotcha:** the two general dialogs take **different props** — `ConfirmDialog` uses `onClose`/`description`/`confirmText`/`cancelText`, `ConfirmationDialog` uses `onCancel`/`message`/`confirmLabel`/`cancelLabel` — so they are not drop-in swaps; `MyBookingCard` shipped importing one and rendering the other, which only shows up as an unresolved-name error from `npm run type-check`.

## Known-incomplete / in flight

- **Two server-side data tasks gate visible features** (`BACKEND-ASK.md` item 58): the operator has not run `npm run backfill:coordinates` (every candidate still returns `distance: null`, so distance is effectively off) or `npm run seed:achievements` (all 10 achievement targets are still the placeholder `1`, so locked progress is suppressed client-side). The new-build *routes* are all live on the deployed server — measured 2026-08-24.
- **Shipped server-side but not yet consumed by the client:** the bookable-slots picker endpoint, availability exceptions UI, post cards rendering the attached `session` performance, the `booking_canceled` / `group_join_request_decided` socket events, `GET /group/join-requests/mine`, and `/matching/nearby` as a radius filter .
- **`Workout.id`/`Exercise.id` are typed `string` client-side but the wire sends numbers** — strict `===` against a string id fails; reconciliation pending.
- **`matchingPreference` has no writer in the app.** The server accepts only 3 of the 14 training types on that field, so Settings was moved to `trainingTypes` (see **Location & coordinates**). The field still feeds 15% of every compatibility score from data nothing populates — `BACKEND-ASK.md` item 59 asks whether it should be widened or dropped.
- **There are no tests, and `npm run type-check` is the only gate** — a green check means it compiles, not that a screen works. Three render-time crashes (a missing `STRINGS` block, a mis-imported dialog, a dead `navigate()`) got through exactly that way, so run a screen before trusting it. See **Verification status** above for what has and has not been exercised on a simulator.
- **Clearing a location still can't clear coordinates on the multipart path — but the fix is now client-side.** The server accepts `null`/`""`/`"null"` on both paths (one code path via multer memoryStorage); it is `updateMyProfileWithImage` that skips null fields and never sends the clear. Send `"null"` strings on the multipart path and this closes.
- **The location permissions in `app.json` are now actually used** (see the device-GPS note under **Location & coordinates**), which closes the old store-review liability. `NSLocationWhenInUseUsageDescription` and the `expo-location` plugin now carry a real explanation rather than the plugin's generic default — **that string only reaches the binary after a `npm run prebuild` / rebuild**, so a dev build made before this change still shows "Allow Bolic to access your location".
- **`STRINGS.SELECT_DATE_TIME` is our placeholder copy**, not client-approved wording.
- **Phone verification is not real** — see the gotcha under **Auth**. `phoneVerified` is client-asserted against a hardcoded `123456`, so the flag cannot be trusted on any existing account.
- **The achievement catalogue is writable by any signed-in user** server-side (`POST /achivement/create|update|delete` are reachable without an admin role — `BACKEND-ASK.md` item 61), and **the Stripe webhook is still unmounted**, so a payment that settles after the request returns is never recorded (item 62). Both are server-side, but worth knowing before trusting `payment_status` or the catalogue.

## Directory map (`src/`)
- `screens/` — one file per screen (plus `screens/group/`); registered in `AppNavigator.tsx`.
- `components/` — reusable UI (forms, cards, modals, top bars, trainer-onboarding steps, stripe provider).
- `services/api/` — RTK Query slices (one per domain); `services/endPoints.ts`, `services/socketClient.ts`, `services/storage.ts` (AsyncStorage wrapper).
- `store/` — Redux store, `userSlice`, typed hooks.
- `contexts/` — `AuthContext`.
- `hooks/` — `useChat`, `useInterFonts`, `responsiveDesignHook`, `useAndroidNavBar`, `useDeviceLocation` (launch-time GPS → profile coordinates).
- `utils/` — `stripeUtils.ts` (PaymentSheet flow), `location.ts` (ArcGIS geocoding + distance formatting).
- `config/` — `constants.ts`, `strings.ts`. `designing/` — responsive system. `types/` — models + navigation + chat types. `validation/` — Formik/Yup auth schemas.
